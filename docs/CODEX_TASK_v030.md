## 性能分析：「校验阶段」5–6MB/s vs 上传阶段 80MB/s（2026-09-12）

- **结论：与限速无关**，是**客户端哈希实现**的瓶颈。`web/src/api.js` 的 `computeFileSHA256` 原实现只在 **≤32MiB** 时使用原生 `crypto.subtle.digest('SHA-256')`；超过该阈值改用**手写纯 JS 的 `IncrementalSHA256`**（因 WebCrypto 无增量/流式摘要 API），纯 JS 位运算吞吐约 5–20MB/s → 与实测 5–6MB/s 完全吻合。上传阶段是分片裸传（loopback 不涉哈希），故可达 80MB/s。服务端 `complete` 阶段（Go 合并分片并计算 SHA-256+MD5）在 GB 级文件上仅需 1–2 秒，不是瓶颈；服务端上传字节级限速（`settings.UploadRateLimit`，默认 0=不限）只作用于分片写入，与校验阶段无关。
- **已实施修复**：把原生 WebCrypto 路径的适用上限从 32MiB 提升到 **256MiB**（可用 `globalThis.FILEBOX_HASH_DIRECT_LIMIT` 覆盖），哈希值语义不变；超过 256MiB 才回退流式纯 JS。预期 ≤256MiB 文件的校验吞吐提升 1–2 个数量级。
- **残余限制**：>256MiB 文件仍走纯 JS（内存换速度的取舍）。后续可选优化：把哈希移入 **Web Worker**（避免阻塞 UI）或引入 **WASM 哈希**（需评估新增依赖）。

## 一、缺陷类

### #1 上传完成后未自动移入「已完成」
- 现状（已核实）：`FilesView.vue` 中 `uploadsDone = computed(() => uploads.value.filter(isUploadTerminal))`，抽屉用它在「已完成」页签渲染；存在两个不同判定（`isUploadTerminal` 与 `done: isUploadComplete(item)` 的持久化恢复路径）。
- 根因假设（待复现确认）：① 上传成功分支未把条目置为终止态（`done`/`status` 未更新），故 `isUploadTerminal` 恒假；② 两套判定不一致，恢复/刷新后状态丢失；③ 与 v026 未合并的 `transferFlow.js`（传输状态机改动）叠加导致。
- 修复方向：统一"终止态"判定为单一 helper（成功/失败/取消三态），上传成功路径显式置 `done` 并 `persistTransfers()`；恢复路径复用同一 helper；补 node 单测覆盖"成功→进入已完成"。
- 验收：上传成功后无需刷新即出现在「已完成」页签；刷新页面后仍在「已完成」；失败/取消不被计入。

### #3 清空时选「删除整个存储目录」疑似只删了当前页文件
- 现状（已核实）：`cleanClearedStorage(userIDs, "whole-tree")` 会对受影响用户执行 `os.RemoveAll(files/<uid>)`；清空本身在服务端按**用户全量**执行（无分页），因此"只删当前页"不可能由后端分页造成。
- 根因假设（按可能性排序，需复现确认）：① **管理员视角作用域错配**——admin 文件列表是全库视图，而清空只清自己名下文件，看起来"只少了几个/没删"；② **前端刷新竞态**——`submitClearAll` 依次 `loadMe/loadFolders/loadFiles`，与 `fileLoadVersion` 版本守卫叠加时可能出现列表未按最新数据刷新；③ v029 已移除全库 scope，管理员的"清空他人文件"改到用户管理后语义更清晰。
- 修复方向：复现并定位后修复（若为 ②，改为清理完成后强制刷新并重置分页/版本号；若为 ①，界面上明确"仅清理我的文件"并给出入口指引到用户管理）；`whole-tree` 增加"目录确实不存在"的验证日志。
- 验收：一次性用户造 2 页以上文件 + 子目录，清空（whole-tree）后 DB 无 ready 记录、磁盘 `files/<uid>` 不存在、列表与统计归零。

### #9 批量分享勾选目录时目录未被分享
- 现状（已核实）：批量分享（独立链接与聚合链接）只接收 `fileIds`；界面勾选目录走 `selectedFolderIds`，未展开为文件 → 目录内文件既不入分享，分享页也无目录结构（聚合分享 meta 仅列文件）。
- 修复方向：① 创建分享时把选中目录**递归展开为其下全部文件**（前端展开或后端接受 `folderIds` 并在事务内展开）；② 聚合分享页保留/展示相对路径（目录层级），至少显示目录名与分组；③ 空目录给出明确提示（无可分享文件）。
- 验收：勾选含 2 个子目录/3 个文件的目录 → 分享页可见目录分组与文件；空目录提示"无可分享文件"；权限仍严格按所有者校验。

### #10 分享链接的"分享者"显示为数字
- 现状（已核实）：`publicShareGroup`（聚合分享）返回 `"createdBy": group.CreatedBy`（**数字 ID**）；单文件分享 `shareMeta` 返回的是 `owner.Username`（用户名，正确）。分享页模板 `ShareView.vue` 直接渲染 `meta.createdBy`。
- 修复方向：聚合分享 meta 增加 `createdByName`（解析用户名，解析失败回退旧值），分享页/列表显示用户名；同时检查收集页（`/u/:token`）是否展示创建者并统一。
- 验收：`/g/:token` 页面与聚合分享详情显示用户名而非数字；未知用户时回退为不显示或 `-`。

### #11 编辑聚合分享时"添加文件"报"文件不存在"（文件实际存在）
- 现状（已核实）：`store.AddShareGroupFiles` 校验 `files.user_id == share_groups.created_by`，不一致即返回 `ErrNotFound`（文案"文件不存在"）。管理员编辑**他人**的聚合分享时，选择器通常列出当前管理员自己的文件 → 必然命中该分支。
- 修复方向：① 编辑弹窗的文件选择器改为列出**该分享创建者**名下的文件（后端为管理员提供按 owner 过滤的文件列表能力）；② 错误语义细化：确实不属于该分享所有者的文件返回 `GROUP_FILE_FORBIDDEN`（"该文件不属于此分享的创建者"），而不是"文件不存在"。
- 验收：管理员编辑他人聚合分享时，选择器展示创建者文件且添加成功；选择非创建者文件时提示准确原因。
